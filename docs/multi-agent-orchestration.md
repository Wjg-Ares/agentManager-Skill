# 多 Agent 协作编排设计（讨论稿 v3）

> 状态：设计讨论完成，未实现。
> 参与：wangjiahui + Claude。日期：2026-09-10。

## 0. 演进记录

| 项 | 原方案 | 现方案 | 原因 |
|---|---|---|---|
| worker 承载 | subagent 为主 | **手动开的交互式会话为主** | subagent 之间无法直接通信；且用户要能看过程、能直接介入 |
| 工作区 | 每个 worker 独立 worktree | **全部共用同一个工作区** | 用户既定前提 |
| 合并策略 | 串行合并 + rebase | **整节删除** | 无 worktree 即无分支合并 |
| 并发写冲突 | 锁是兜底 | **锁是生命线** | 同工作区下覆盖会直接丢代码，git 没有介入机会 |
| Write 工具 | 建议禁用 | **不禁用** | 锁在落盘前就拦住了，Write 与 Edit 风险等同 |
| 构建 | 未约束 | **收归主 agent** | 并发 `dotnet build` 会写坏 bin/obj |
| 任务边界 | 主 agent 派活时划定 | **worker 自行声明，主 agent 汇总** | 划边界的人找错了；声明文件同时充当锁表 |
| 规则常驻 | 指针 + skill + 回灌 + hook 四层 | **rules 一层** | 共用工作区，rules 全员加载且 compact 不冲掉，四层是过度设计 |
| 存储（v3） | JSON 文件 + 目录锁 + 手写原子写 | **SQLite** | 并发原子性由数据库保证，认领文件成为一次事务，仲裁可交给唯一索引；Python 自带 `sqlite3`，用户无需安装 |
| 交付传递（v3） | 摘要 + 文件路径 | **摘要 + deliverable ID** | 内容存库，主 agent 按需查，进一步压缩主上下文 |
| 队列推进（v3） | 事件驱动，主 agent 顺手看一眼 | **绑定到审批动作** | 每次用户说满意，主 agent 必须查队列并给出「1 执行 / 2 删除」 |
| SKILL.md（v3） | 未约束 | **尽量薄，逻辑下沉到程序** | SKILL.md 每次进上下文烧 token，脚本执行不烧，只有输出烧 |

## 1. 目标与前提

一个主 agent 统一接活，分派给若干 worker 并行执行。**用户只跟主 agent 提需求**，
但保留随时进入任意 worker 窗口直接干预的能力。

**硬前提：所有 agent 共用同一个工作目录。** 本文所有设计以此为基础。

## 2. 角色

| 角色 | 承载 | 职责 |
|---|---|---|
| 主 agent | 交互式会话 | 接需求、派活、维护账本、转发追问、仲裁冲突、执行 git 与构建 |
| worker × 3 | **手动开的交互式会话** | 执行任务、产出文件、交付摘要、与其他 worker 直接协商 |
| subagent | 由主 agent 或 worker 临时 spawn | **仅作辅助**，干一次性小活（全仓库搜符号、批量读文件等），不参与主架构 |
| 用户 | — | 提需求、审批每次交付、可直接进任意窗口拍板 |

并发上限 **3 个 worker**。满了则任务挂队列（不由主 agent 自己干，避免污染调度上下文）。

### 为什么 worker 用交互式会话而不是 subagent

1. **subagent 之间无法直接通信**——它们发出的跨会话消息会以父会话地址发出、回复也回到父会话，
   彼此够不着。而本方案第 6.3 节的"两个 worker 自行协商"要求 worker 之间能直连
2. **过程可见**——每个 worker 有独立终端，出问题能当场看到
3. **用户可就地干预**——技术细节的争执可以直接在 worker 窗口拍板，
   **不必进主 agent 的审批队列**。这是第 5.3 节审批瓶颈的泄压阀
4. **上下文长期持续**——不会因单个任务结束而销毁

代价：worktree 自动隔离用不上（本方案本就不隔离）；worker 需要人工开窗口并注册。

## 3. 身份与注册

会话名（如 `cdc-1f`）是**启动时随机生成的，重开即变**。账本若直接记会话名，
worker 一重启账本立刻失效。因此加一层注册：

```
worker-1  ←  cdc-1f  (session_id: 572dda2f-…)
worker-2  ←  cdc-9x  (session_id: …)
```

- worker 启动后先注册，把当前会话名与 session_id 绑到稳定角色名上
- 主 agent 只认 `worker-1/2/3`，由脚本翻译成当前实际地址
- **存活探针挂在这一层**：拿注册表里的 session_id 去 `claude agents --json` 查，
  查不到即判定该 worker 已死，回收其占用

## 4. 调度协议

### 4.1 双标记（不依赖 status）

`busy/idle` 是瞬时快照，查到与派活之间存在窗口，不能作为调度依据。改用双标记：

- **任务开始标记**：主 agent 派活时写入
- **任务结束标记**：交付且**用户审批通过后**，由主 agent 写入

标记必须带 **任务 ID + 时间戳**，否则同一 worker 干过多轮后无法分辨标记归属。

**空闲判定**：该 worker 最后一条记录是已审批的结束标记。
用户没说满意，slot 就一直占着——这正是保护追问上下文的机制。

### 4.2 账本

主 agent 维护，**必须落库**（SQLite，见 §10.3）。主 agent 会 compact，
一旦失忆就不知道派了什么活给谁，调度即崩。账本是重建状态的唯一来源。

语义（字段定稿见 §10.3）：任务 ID、worker 角色名、状态、优先级、任务边界、
审批状态、创建/派发/交付/审批时间。

### 4.3 队列

3 个 slot 全占则任务入队，**队列即 `tasks` 表中 `status='queued'` 的行**，不另建结构。

推进方式**绑定到审批动作**：

> **每次用户对任一 worker 说"满意"时，主 agent 必须顺带查一次队列。**
> 有待办则给出选项：**1 执行　2 删除这条待办**。

这样设计的意义：把队列推进挂在"用户说满意"这个他本来就在场的时刻，
不需要额外的轮询、定时器或提醒机制。**实现时不要另起一套通知。**

队列支持**优先级调整**，需有对应命令（见 §10.2）。
仅对"worker 卡死未交付"挂一个长间隔定时兜底。

## 5. 交付与审批

### 5.1 产出与摘要分离

worker 交付时：

- **完整产出** → 落库（`deliverables.content`）
- **发给主 agent 的消息** → 只有**四行摘要 + deliverable ID**

**主 agent 只吃摘要，绝不读全文。** 需要细节时凭 ID 去库里查，
用户要看则由主 agent 给出 ID / 由用户自己查，不经主 agent 上下文中转。
这是防止主 agent 被 3 路完整产出撑爆的核心措施。

### 5.2 摘要格式（固定，超出即打回）

```
改了什么：<一到两行>
影响面：<涉及的文件 / 接口 / 表>
风险点：<无则写"无">
待你确认：<无则写"无">
是否已编译验证：否（构建权在主 agent）
```

### 5.3 审批：全部都审

**决定：每一次交付都要用户审批。**

- 满意 → 主 agent 打结束标记 → slot 释放
- 不满意 → 追问转发给**同一个** worker（上下文还在，换人前功尽弃）

已知代价：并行执行 + 串行审批，用户是吞吐瓶颈。两条缓解：

1. **摘要压到四行**（见 5.2），压低单次审批成本
2. **就地干预**：技术细节的争执直接在 worker 窗口解决，不进审批队列

串行审批同时**换来一个好处**：每次只放行一份改动，主 agent 那次构建只包含这一份，
编译挂了责任清晰、直接打回。若审批并行，三份改动混在一起构建，挂了都找不到是谁。

### 5.4 审批通过 = worker 可以清空上下文

worker 连干多个任务，上下文迟早 compact。**结束标记正好是可清空的信号**：
用户说满意 → 打结束标记 → 该 worker `/clear`，下个任务从干净上下文开始。
没说满意之前不清，追问上下文完整保留。

丢掉的只是 worker 对项目的"记忆"，而那本就该从 CLAUDE.md 和代码现读，不该靠记。

## 6. 并发写冲突（核心机制）

### 6.1 为什么是生命线而不是兜底

worktree 隔离时，两个 agent 改同一文件是各改各的副本，冲突推迟到合并，git 会拦住，
最坏是手工解一次——**改动不会丢**。

共用工作区时，A 刚写完、B 拿旧内容一覆盖，**改动直接消失，无提示，git 无从介入**。

因此锁不是"防冲突"，是**防数据丢失**。没有它整套架构不能跑。
限制并发到 3 个只降低撞车概率，不消除撞车。

### 6.2 文件声明：边界由 worker 自己声明，不由主 agent 划定

**worker 在改代码前，先把本次涉及的文件登记进 `claims` 表。**

这条解决了"任务边界怎么描述"的死结——边界划不清，是因为划边界的人找错了。
主 agent 事前拆到文件级，成本比自己干还高；而 worker 干着干着自然就知道要动哪些文件。
主 agent 只需查一次表，即可获得全局视图。

好处：

- **声明记录就是锁表**，不必再单独维护一份
- 支持**增量追加**——干到一半发现要动新文件，追加声明即可，不必一开始想全
- 主 agent 派活前先查一次，可**主动避开**已被占用的文件，
  冲突在派活阶段就消掉一半，不必全堆到 hook 去拦

**仲裁交给数据库，不要在应用层扫描比时间戳**：

```sql
CREATE UNIQUE INDEX ux_claims_active ON claims(file_path) WHERE released_at IS NULL;
```

"同一文件同时只能有一个活跃声明"由数据库保证，**INSERT 冲突即代表已被占用**。
这比"读出全部声明→比较时间戳→再写入"可靠得多，且天然没有竞态窗口。
（SQLite 支持部分索引，可放心用。）

### 6.3 锁（基于声明实现）

- **拦截点**：`PreToolUse` hook，覆盖 Edit / Write / NotebookEdit
- **判定**：查 `claims` 表，目标文件若存在他人的活跃声明则否决
- **key**：文件绝对路径（共用工作区，无需仓库相对化）
- **粒度**：**按文件判定，按方法协商**——文件级好实现，真假冲突交给双方一次对话判断
- **防死锁**：靠存活探针（§3），worker 已死则其声明作废。TTL 仅作最后兜底
- **释放**：任务审批通过后置 `released_at`（软释放，保留追溯）

### 6.4 撞锁后的协商流程

```
worker-A 要改 CollectTaskService.cs
  → hook 查锁表，发现 worker-B 持有
  → 否决，拒绝理由里给出【持有者的会话名】（不是 session_id，要能直接当地址用）
  → A 直接发消息给 B：我要改哪个方法、为什么
  → 两人自行协商：真冲突就让路 / 假冲突（改的是不同 region）就交接锁
  → 谈不拢 → 报主 agent 仲裁
  → 主 agent 也定不了 → 问用户
```

用户可在**任一环节**直接进那两个窗口拍板，不必等升级到主 agent。

### 6.5 残留风险：TOCTOU

A 读文件 → 释放锁 → B 修改 → A 重新拿锁 → 基于旧内容写入。
Edit 会因 `old_string` 不匹配而失败，Write 不会。

缓解（可选，先不做）：拿锁时记录文件 hash，落盘前比对，变了就拦。
先观察实际发生频率再决定要不要加。

## 7. 权限收归主 agent

### 7.1 git 写操作

worker 只准读（`git diff` / `git log` / `git status`）。
`commit` / `checkout` / `stash` / `rebase` 一律报主 agent 执行——
共用工作区里这些是全局操作，一个 worker 动全员遭殃。

### 7.2 构建

**worker 禁止执行任何写 `bin/obj` 的命令**：`dotnet build` / `run` / `publish` / `test` / `restore`。
并发构建会互相锁文件、写坏产物，且报错看不出根因。

构建由用户向主 agent 主动下达。链路闭合为：

```
worker 改代码 → 交付（标注"未编译验证"）→ 用户审批 → 主 agent 构建 → 通过才算完成
```

代价：语法错、缺 using 这类低级问题要拖到主 agent 那步才暴露，返工一轮。可接受。

### 7.3 实现方式

不靠自觉，**用 hook 硬拦**：`PreToolUse` 看到 Bash 命令先查注册表，
本会话是 worker 且命中禁用清单就否决，理由写明"构建/git 权在主 agent"。
与 §6.2 的锁共用同一套 hook 基建，无额外成本。

## 8. 规则如何常驻

worker 是手动开的会话，没有 spawn 时注入 prompt 的机会，必须自己知道交付格式、
协商规则、何时打标记、何时声明文件。

**因为全部 agent 共用同一工作目录，`.claude/rules/` 天然被所有会话加载**，
规则写一次全员生效，不需要分发。且它与 CLAUDE.md 一样属于 system prompt 级别的常驻注入，
**compact 不会将其冲掉**——不存在"干到第三个任务就忘了规则"的问题。

因此只需两层，不必引入 skill 加载或回灌机制：

| 类型 | 承载 | 例子 |
|---|---|---|
| **静态规则** | `.claude/rules/` | 交付四行格式、禁构建禁 git 写、改代码前先声明文件、撞锁后先协商再升级 |
| **动态状态** | 脚本现查 | 我是哪个 worker、当前什么任务、别人声明了哪些文件、队列里还有什么 |

分界很清楚：**规则是不变的，写进 rules；状态是每时每刻在变的，rules 里写不了，只能查。**

规则可写成条件式（"若注册表中登记了本会话为 worker，则遵守以下……"），
这样临时开的普通会话不受约束。

## 9. 失败处理

- **存活探针**：worker 崩溃后开始标记永远等不到结束标记，slot 永久占用 → 查活性，已死则回收
- **超时重派**：超阈值未交付则回收重派，重派前须确认原 worker 确已死亡，避免双写
- **死信**：连续失败的任务停止自动重派，标出来交给用户

## 10. 实现路线

### 10.1 不引入 LangGraph

- 它的价值在复杂条件分支的状态机与状态持久化；本方案是最简单的 worker pool，用不上
- 更实际的代价：LangGraph 的节点是它自己调 API 的 LLM，**不是 Claude Code 会话**。
  换过去意味着 Edit/Bash/权限体系/hooks 整套丢失，需再套一层 `claude -p` 调起，白增一层
- AutoGen / CrewAI 同理

借鉴任务队列的成熟经验即可（账本在调度器手里、超时重派、死信队列），已吸收进 §4、§9。

### 10.2 半代码：规则进 rules，逻辑进程序，SKILL.md 尽量薄

分界原则：**需要判断的给 agent，不需要判断的给程序。**

| 部分 | 承载 | 内容 |
|---|---|---|
| 规则 | `.claude/rules/` | 何时派活、摘要格式、仲裁流程、禁构建禁 git 写 |
| 逻辑 | Python 程序 | 账本读写、注册、查空闲、状态流转、队列与优先级、仲裁、存活探针 |
| 强制 | hook | 锁拦截、构建/git 禁用、释放锁 |

**SKILL.md 必须薄。** SKILL.md 的内容每次都进上下文烧 token，
而程序执行不烧、只有输出烧。因此：

- SKILL.md 只写"**什么场景调哪个命令**"，不写业务逻辑、不写分支判断
- 判断能编码进程序的一律编码进去，**让命令输出直接给出下一步该做什么**
- 例外：需要理解代码语义的判断（如"这两个 worker 的冲突是真是假"）程序做不了，留给 agent

命令做成**一组动词**，不要让 agent 自己读写存储：

```
am setup                           首次初始化：建库、落 hook 配置、注册主 agent
am register <角色名>                worker 启动时登记
am status                          账本 + 各 slot 状态 + 队列（输出自带下一步指引）
am claim <worker> <task>           派活，打开始标记
am declare <task> <文件...>         worker 声明将要改动的文件
am deliver <task> <摘要>            worker 交付，返回 deliverable ID
am show <deliverable-id>           主 agent 按 ID 查完整产出
am approve <task>                  用户满意后：打结束标记、放 slot、**并返回队列待办**
am queue [--priority <id> <n>]     查看队列 / 调整优先级
am reap                            存活探针，回收死 slot
```

（以上是 **Python CLI 子命令**，供 agent 与 hook 调用；命令名除 `setup` 外均为初稿，需与用户确认。）

> **对外暴露的 slash 命令一律用 `/am-***` 格式**（用户硬性要求），
> 如 `/am-setup`、`/am-status`。两个层面别混——slash 命令是会话里敲的，
> CLI 子命令是程序内部调的。

主 agent 只做决策，状态一律经程序落库——**compact 之后调一次 `am status` 即完全恢复**。

### 10.3 存储：SQLite

Python 自带 `sqlite3`（实测引擎 3.45.1），**用户无需安装任何数据库**，零依赖成立。

必须表：`registry` / `tasks`（含队列）/ `deliverables` / `claims` / `events`。
连接必开三个 PRAGMA：`journal_mode=WAL`、`busy_timeout`、
`foreign_keys=ON`（**SQLite 默认关闭**，不显式打开则外键约束形同虚设）。

耐用性要求：状态用文本枚举不用魔法数字、时间统一 ISO8601 UTC 文本、
每表带 `created_at`、软删除而非物理删除、schema 版本用 `PRAGMA user_version` 并配迁移函数。

**表结构定稿前须经用户过目。**

### 实现阶段新确定的（v4）

| 项 | 结论 | 依据 |
|---|---|---|
| **hook 怎么装** | **插件自带 `hooks/hooks.json` + `${CLAUDE_PLUGIN_ROOT}`**，装上即生效，**不写用户的 settings.json**，卸载自动干净 | 官方 `claude-security`、`hookify` 插件都是这么做的。BRIEF §9 那个难点因此消失 |
| **session_id 怎么拿** | 环境变量 **`CLAUDE_CODE_SESSION_ID`**，零成本 | 实测 |
| **会话名怎么拿** | `claude agents --json` 按 sessionId 匹配 `name`。**只在 register 时查一次存进 registry**，之后 guard 走库 | 实测；该调用约 1 秒，不能进热路径 |
| **没声明就改文件怎么办** | **hook 自动补一条声明**再放行，并在 `systemMessage` 里说明 | 靠自觉必然会漏，一漏锁就形同虚设；自动补让锁始终成立且行为可见 |
| **hook 全局生效的代价** | 无关项目 **69ms/次**（Python 冷启动基线 46ms），有账本项目 108ms。判否逻辑内联在 hook 里，**不导入 poolkit** | 实测；导入 poolkit 要 +43ms，绝大多数 Edit 发生在无关项目 |
| **slash 命令粒度** | **4 个**：`/am-setup`、`/am-status`、`/am-worker`、`/am-approve`。其余动词只做 CLI | 每个 skill 的 description 都常驻上下文，命令拆太细反而费 token |
| **配置放哪** | 库里的 `settings` 表，`config set` 改 | 跟着项目走，不污染 `settings.json` |
| **不占 C 盘** | `/am-setup --vendor` 把脚本、hook、四个命令全部落地进项目的 `.claude/`，**自检通过后自动卸掉插件安装** | 插件本体必然装在 `~/.claude`（Claude Code 写死，实测 `--scope project` 也只改「声明在哪」，installPath 仍在 C 盘），只能让运行时文件搬进项目。落地后规则与 SKILL.md 里的路径全部改写成项目内绝对路径，不依赖 `${CLAUDE_PLUGIN_ROOT}` |
| **卸插件的门槛** | 先清掉 `CLAUDE_PLUGIN_ROOT` 跑一次落地的脚本，过了才卸；脚本源在插件安装目录之外（如 `--plugin-dir` 指向的仓库）则一概不动 | 删目录的操作必须有退路：落地缺文件又把插件删了，用户两头空；而误把用户的开发仓库当插件删掉，后果更严重 |
| **临时文件放哪** | 默认 `<项目根>/.claude/am/tmp`，setup 自动设好并建出目录，**不需要用户配置** | 原先要用户自己指一个路径（`--scratch-dir`），用户反问「就不能默认放项目里固定文件夹吗」—— 他是对的：跟着项目走、不同项目天然隔开、`.claude/am/` 本来就在 .gitignore 里 |
| **清理必须放最后**（事故） | `--vendor` 的步骤序为：复制文件 → 装 hook → 装规则 → **最后**卸插件；且规则模板从 `base` 读、并随落地一起复制进项目 | 真出过事故：卸插件原本排在装规则之前，把 `_install_rules` 还要读的 `templates/` 连同插件一起删了 —— 报「插件文件不完整」，项目里什么都没写成，插件还没了。凡是「清理」与「读源文件」并存的流程，清理一律排最后 |
| **`${CLAUDE_PLUGIN_ROOT}` 靠不住** | SKILL.md 里给出不依赖变量的定位兜底；`--vendor` 落地时把四个命令的路径全部改写成项目内绝对路径 | 实测该变量在会话里可能为空，原样进 shell 后路径塌成 `/scripts/pool.py`，git bash 再解析成 `<Git 安装目录>\scripts\pool.py`。落地之后不含任何变量，这类问题一次性消失 |
| **谁算「往 Temp 扔垃圾」** | 落在项目根之下的一律不算，哪怕项目本身就在系统 Temp 里 | 有人就在临时目录里试东西，那时整个项目路径都含 `AppData\Local\Temp`，一刀切会把他所有代码都拦住、连锁判定都轮不到 |
| **规则副本何时更新** | 写入时记内容哈希，下次比对：与基准一致=用户没改过，直接更新；不一致=手改过，保留并提示 `--force-rules` | `.claude/rules/` 是副本，插件升级只换模板不动副本；光比「和模板一不一样」分不清「没改过」与「手改过」，而这两者处理方式相反 |
| **规则里的变量不展开** | setup 写入时就把 `${CLAUDE_PLUGIN_ROOT}` 换成真实绝对路径 | `.claude/rules/` 是常驻规则文本而非 skill，Claude Code 只对 SKILL.md 做变量替换；shell 里也没有该变量，留着字面量路径会塌成 `/scripts/pool.py` |
| **控制台编码** | `pool.py` 与 `hooks/pretooluse.py` 启动即把 stdout/stderr 强制为 UTF-8 | Windows 控制台是 cp936，输出里的 ✓ 会抛 UnicodeEncodeError。hook 崩掉尤其危险：那次 Edit 会失去保护，而用户以为锁在生效 |
