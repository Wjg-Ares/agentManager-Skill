# 多 Agent 协作编排规则

> 本文件由 `/am-setup` 装进项目。所有共用这个工作目录的会话都会加载它，
> 因此规则写一次全员生效，且不会被 compact 冲掉。

**先判断本条是否适用于你**：只有在编排账本里登记过角色的会话才受下面的约束。
不确定就执行 `python "${CLAUDE_PLUGIN_ROOT}/scripts/pool.py" whoami`；
输出「没有登记角色」的话，本文件与你无关，正常干活即可。

下文的 `P` = `python "${CLAUDE_PLUGIN_ROOT}/scripts/pool.py"`。

## 如果你是 worker

1. **改任何文件之前先声明**：`P declare <文件...>`。
   干到一半要碰新文件就再声明一次，不必一开始想全。
   （忘了也没关系，hook 会自动替你补一条声明，但主动声明能让主 agent 提前避开冲突。）

2. **不许构建、不许 git 写**。`dotnet build/run/test/publish/restore`、
   `git commit/checkout/stash/rebase/reset/push` 一律报给主 agent 执行。
   共用工作区里这些是全局操作，一个人动全员遭殃。hook 会拦你。

3. **交付格式固定，缺项会被打回**：

   ```
   P deliver <任务ID> --changed "改了什么" --impact "涉及的文件/接口/表" \
             --risk "无" --confirm "无" --content-file <完整产出文件>
   ```

   发给主 agent 的**只有五行摘要 + 交付 ID**，完整产出留在库里。
   不要把产出全文贴给主 agent —— 它的上下文要同时接三路，撑爆了整个调度就崩了。

4. **撞锁先协商，别升级**。拒绝理由里会给出持有者的会话名，那就是地址，
   直接发消息问它改的是哪个方法。真冲突就等，假冲突让它 `P handoff <文件> --to 你`。
   谈不拢才报主 agent。

5. **用户说满意之前不要 `/clear`**。被打回时追问的上下文全在你这儿。
   审批通过后主 agent 会通知你，那时清干净，下个任务从头开始。

## 如果你是主 agent

1. **只吃摘要**。需要细节才 `P show <交付ID>`，用户要看长产出就
   `P show <ID> --out D:\claude-tmp\...` 给路径，别让它过你的上下文。

2. **派活前先看 `P status` 里已被声明的文件**，主动避开，冲突在派活阶段消掉一半。

3. **用户每次说满意，都走 `P approve <任务ID>`**，它会把队列待办和
   「1 执行 / 2 删除 / 3 改优先级 / 0 不处理」一起给出来 —— 把选项转达给用户，
   等他选完再动手。不要另起一套提醒或轮询机制。

4. **构建是你的活**。worker 交付时标的是「未编译验证」，
   审批通过 → 你构建 → 通过才算真完成。挂了直接打回给原 worker。

5. **失忆了就 `P status`**。账本在库里，不在你的上下文里。

## 用户随时可以介入

技术细节的争执，用户可以直接进任意 worker 窗口拍板，不必等升级到主 agent。
